## 1. What has to be decided

API_DESIGN §8 already fixes the API: `civkit.call(...)`, `list()`, `describe(id)`, typed functions per calculation, three
input forms for quantities (`"2.4 m^2"`, `(2.4, "m^2")`, `civkit.Q(2.4, "m^2")`), `Q` results with `.to()`, and
`MISSING_UNIT` for a bare number on a dimensional input. What remains is **which Pythons and platforms, how the
package is built and shipped, how thin the Rust layer is, and which gates prove it works**.

## 3. The design this proposal adds

### 3.1 A thin Rust layer, everything else in plain Python

The Rust extension exposes four functions and nothing else:

| Rust (crate `civkit-python`, module `civkit._civkit`) | Does |
|---|---|
| `call_json(request: str) -> str` | `Registry::with_builtins().call_json(request)`, unchanged |
| `list_json() -> str` | every descriptor, as JSON |
| `describe_json(id: str, version: int \| None) -> str` | one descriptor, as JSON |
| `version() -> str` | the CivKit version |

Everything else is ordinary Python in `civkit/__init__.py` and a few modules: turning `"2.4 m^2"`, tuples and `Q` into
the JSON request; building `Result` and `Q` objects from the response; raising errors; generating typed functions from
descriptors. **Why:** the Rust surface stays tiny and stable (like the C ABI of D-6), and parity with
`Registry::call_json` holds by construction, because every call goes through it. The Python layer does no validation
of its own; it only reshapes input and output.

### 3.2 Results and errors

- `civkit.call(...)` returns a `Result` with `.outputs` (name → `Q`, or a list of `Q` for list outputs), `.trace`,
  `.warnings`, `.references`, `.assumptions`, `.version`, and **`.to_dict()`, which equals the contract JSON exactly**.
- Contract errors raise **`civkit.CivKitError`** with `.code`, `.input`, `.index` and `.message`. Several errors in one
  response raise one `CivKitError` whose `.errors` lists them all, in order.
- Warnings stay in `Result.warnings`; nothing is printed or emitted through Python's `warnings` module.

### 3.3 Typed functions

`civkit.fluids.open_channel.manning_trapezoidal(bottom_width="1.5 m", …)` is generated **at import time** from the
descriptors in the installed wheel, with keyword-only arguments and a docstring built from the descriptor (title,
summary, inputs with units, the D-24 validity statement). Each function sends the descriptor version it was generated
from (API_DESIGN §8). A `.pyi` stub file generated by a script gives editors and type checkers the same signatures;
CI regenerates it and fails on any difference.

### 3.4 No runtime dependencies

The package depends on nothing outside the standard library. pandas or NumPy conversions (FEATURE_PROPOSALS FP-09) are
later and optional. The package itself makes no network calls and no intentional file writes, at import or when calculating (OFFLINE_POLICY rule 8 bans fetching data at import). Normal interpreter bytecode caches (`.pyc` in `__pycache__`) are Python's own and are excluded; a zero-file-write test is not required.

### 3.5 Build and CI

- `maturin build --release`, with `--compatibility manylinux2014` on Linux; one abi3 wheel per target.
- **CI build matrix:** the five targets. **CI test matrix:** every Python 3.11–3.15 on Linux x86-64, and at least one
  Python on each other target. Any third-party action used for building is pinned by commit SHA, as the existing
  workflow does.
- **Offline install check** on each target: install the built wheel with `pip install --no-index --find-links dist civkit`
  with networking disabled for the step, then run one list calculation and one contract error.
- PyPI publishing is **not** part of Phase 3. It belongs to the 0.1 release decision, together with the naming risk in
  [COMPETITIVE_LANDSCAPE.md](COMPETITIVE_LANDSCAPE.md) §10.

| **Q-D** | Errors as one exception class `CivKitError` with `.code`, `.input`, `.index`, `.message` and `.errors` (§3.2). | **As proposed.** One class keeps `except` simple; the code distinguishes cases. |

| **Q-F** | No runtime dependencies; no network calls or intentional file writes by the package (interpreter bytecode caches excluded) (§3.4). | **As proposed** (OFFLINE_POLICY rule 8). |
| **Q-G** | Gates, mirroring ADR 0013 (below). | **As proposed.** |

### The gates (Phase 3 Python is not done until all pass in CI)

| Gate | What must be shown |
|---|---|
| **P1 — offline install** | On each of the five targets: the wheel installs with networking disabled and runs a calculation. |
| **P2 — versions** | The Python test suite passes on CPython 3.11, 3.12, 3.13, 3.14 and 3.15. |
| **P3 — parity** | For every reference case in `tests/reference/`: on success, `civkit.call(...).to_dict()` equals `json.loads(call_json(request))` exactly; on error, the raised `CivKitError`'s fields and full `.errors` list equal the parsed error envelope. |
| **P4 — errors** | `CivKitError` keeps `code`, `input`, `index` and the full list for multi-error responses, including list-element errors. |
| **P5 — no network at import** | Importing `civkit` and calling a calculation succeeds with sockets blocked. |
